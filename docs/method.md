# Method

The tool answers one question: is the release setup of this desktop app in order before it ships? It reads the project's files as data, never runs a build, and turns each difference from the official documentation into a finding with a severity, a file and a line. Everything it knows about versions, option names and security items comes from official pages that are saved under [research/sources](../research/sources) and listed in [rules-and-sources.md](rules-and-sources.md). A test compares the names and the quoted sentences in `src/data.js` and in the findings with those saved pages, so the tool and its sources cannot drift apart without a failing test.

## Severities

- **error**: the documentation calls it a failure or a risk, or it makes a check impossible. An unsupported Electron major, a `webPreferences` value that breaks an item of the security checklist, an update address over plain http, a Tauri updater without a `pubkey`, a certificate or key file in the project, a configuration file that cannot be read.
- **warning**: guidance of the platform vendors that a release should follow, but that a project may have met in a way the files cannot show: no Windows signing, no macOS signing, no notarization, a turned-off hardened runtime, a version below the latest minor release.
- **info**: something the tool did not or could not check, said in so many words: no releases file, a setting written as an expression, a configuration format it does not read, no update setup, Tauri notarization through environment variables.

By default only errors fail the run. `--fail-on warning` fails on warnings too. Info never fails the run.

## The checks

**1. Electron version (`electron-unsupported`, `electron-not-latest-minor`, `electron-support-not-checked`, `electron-version-unknown`).** The version is the `electron` dependency of `package.json`. A version written as `43.7.7`, `^43.0.0`, `~43.0.0`, `43`, `43.x` or with a pre-release part is read; a tag (`latest`), a range with an operator (`>=40`), a path, an address or a value that is not a string is `electron-version-unknown`, and its support is not claimed. Electron's policy, on its timelines page, is "The latest three stable major versions are supported by the Electron team". With a releases file, the stable majors are listed from newest to oldest, and the first three are supported. A major outside them is `electron-unsupported`, an error. The same page says "We only support the latest minor release for each stable release series", so a version in a supported line whose minor is below the latest minor of the line is `electron-not-latest-minor`, a warning. This applies to an exact version and a `~` range, which cannot move to a later minor; a `^` range or a version with a missing part follows the later minors, so it is not flagged. A major newer than every stable release in the file is noted and not judged. Without `--releases` the tool cannot know which majors are the latest three, so it reports `electron-support-not-checked` and the check's result is `not checked`. The security page also asks to "Use a current version of Electron" (item 16), which the fix text quotes.

**2. Electron security settings (`insecure-node-integration`, `insecure-context-isolation`, `insecure-sandbox`, `insecure-web-security`, `insecure-content`, `setting-not-literal`, `web-preferences-not-found`).** The source files are scanned with a small tokenizer that skips comments, strings, template literals and regular expressions, so text inside them is not read as code. Every object written after `webPreferences:` or `webPreferences =` is read for its top-level properties. A property whose whole value is `true` or `false` is a literal; anything else (a variable, a call, a negation, a shorthand property) is an expression and is `setting-not-literal`, info. A spread is skipped. The five settings are judged against the unsafe value that the security page shows:

| Setting | Unsafe value | Item of the security checklist it breaks |
| --- | --- | --- |
| `nodeIntegration` | `true` | 2. Do not enable Node.js integration for remote content |
| `contextIsolation` | `false` | 3. Enable Context Isolation |
| `sandbox` | `false` | 4. Enable process sandboxing |
| `webSecurity` | `false` | 6. Do not disable webSecurity |
| `allowRunningInsecureContent` | `true` | 8. Do not enable allowRunningInsecureContent |

A setting that is not written in the source is "not found in source", in the report and in the JSON (`status`). It is not called safe: the tool cannot see a default, a value set elsewhere, or a window created in code it did not read. The JSON carries, for each setting, the version since which the page says the safe value is the default (Electron 5 for `nodeIntegration`, 12 for `contextIsolation`, 20 for `sandbox`), as a fact of the page and not as a verdict. Item 2 concerns windows that load remote content; the tool cannot see what a window loads, and the message says so. When no `webPreferences` object is found at all, the result of the check is `not checked`.

**3. Windows signing (`windows-signing-missing`, `windows-signing-disabled`).** For electron-builder the signing is `win.sign`: an object with a `type` of `signtool`, `hsm`, `pkcs11` or `azure`, or a string for a custom signing module. `false` or `null` turns it off (`windows-signing-disabled`). The older `win.signtoolOptions` and `win.azureSignOptions` count as configured. When `win.sign` is not set, electron-builder signs with a certificate that it finds in the environment (`WIN_CSC_LINK` or `CSC_LINK`), which the files cannot show; the tool reports `windows-signing-missing`, says so in the message, and the way to settle it is to set `win.sign` in a file. For Electron Forge, `packagerConfig.windowsSign`, or `windowsSign` or `certificateFile` in a maker's `config`. For Tauri, a `bundle.windows.certificateThumbprint` or a `bundle.windows.signCommand` that is not null or empty. The reason is Microsoft's code signing page, which says that signing consecutive releases with a consistent publisher identity lets publisher reputation build over time.

**4. macOS signing and notarization (`macos-signing-missing`, `macos-signing-disabled`, `macos-signing-adhoc`, `macos-hardened-runtime-off`, `macos-notarization-missing`, `macos-notarization-env`).** For electron-builder: `mac.sign.identity` names the certificate; `null` (or `mac.sign: null`) skips signing; `"-"` is an ad hoc signature, which has no Developer ID and cannot be notarized. `mac.sign.hardenedRuntime` is `true` by default and `false` is a warning, because notarization requires the hardened runtime. `mac.notarize` must be `true`: electron-builder's notarization needs it, and the Apple credentials come from environment variables, which the files cannot show. A `notarize` that is missing or `false` is `macos-notarization-missing`, and the message says which. For Electron Forge: `packagerConfig.osxSign` (the object must exist) and `packagerConfig.osxNotarize`. For Tauri: `bundle.macOS.signingIdentity` (`"-"` is ad hoc), `bundle.macOS.hardenedRuntime` (default `true`), and notarization through environment variables, reported as `macos-notarization-env`, info. The reason is Apple's notarization page, which lists the protections the notary service requires.

**Platforms.** `--platforms windows` or `--platforms macos` leaves the other platform out. A left-out platform has no findings and its check is `skipped`, never `pass`.

**5. Auto-update (`update-insecure-url`, `updater-no-pubkey`, `updater-insecure-transport`, `updater-config-not-found`, `no-auto-update`).** For electron-builder, a `publish` key at any level of the configuration up to a depth is an update setup; inside it, a `url`, `endpoint` or `publicUrl` that starts with `http://`, and a `protocol` of `http`, are `update-insecure-url`. The `electron-updater` dependency also counts as an update setup. For Tauri, `plugins.updater` is the setup. Without a `pubkey` it is `updater-no-pubkey`: the updater page says the `pubkey` "has to be the public key generated from the Tauri CLI", and the app cannot verify what it downloads without it (a key set in the Rust code is not read, and the message says so). An endpoint that starts with `http://` is `update-insecure-url`, and `dangerousInsecureTransportProtocol: true` is `updater-insecure-transport`; the page says that "TLS is enforced in production mode" and that the setting "allows the updater to accept non-HTTPS endpoints". When `Cargo.toml` names `tauri-plugin-updater` and the configuration has no `plugins.updater`, the keys may be set in code, and the tool says it did not check them. No update setup at all is `no-auto-update`, info.

**6. Certificate and key files (`committed-key-file`).** A file with the extension `.pfx`, `.p12` or `.key`, or a `.pem` file that holds a PEM header and a private key, inside the project folder. The finding names the path and the kind. The contents are never put in a report. The tool cannot ask git whether the file is tracked; it reports every such file, and the message says "if git tracks it".

**Reading problems (`config-unreadable`, `config-not-read`, `source-not-read`, `tauri-v1-layout`).** A configuration file that is not JSON or the supported YAML subset, is not an object, or is not a regular file is `config-unreadable`, with the line the reader stopped at. A configuration of a format the tool does not read is named in `config-not-read`. A source file that is too large or too many files are named in `source-not-read`.

## Output

The report keeps the state of every check, not only the failures: the Electron version and the releases used, every `webPreferences` setting with its locations or "not found in source", the signing and update state per packager, and the six results (`pass`, `fail`, `warn`, `info`, `not checked`, `skipped`, `n/a`). Findings are sorted by severity, then by check, file, line and subject, so the same files give the same report on every system. Text that comes from the input goes through `safeText` before it reaches a report.
